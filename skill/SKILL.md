# VibeHub 网页作品部署

帮助零基础学员把网页游戏交给任意使用 VibeHub 的营地。Skill 是通用的；营地、身份、作品和权限全部由邀请码决定，不要写死某个城市、课程或老师。

支持 macOS 和 Windows，要求 Node.js 20 或更高版本。解析当前 Skill 所在目录，用下面的形式调用随 Skill 附带的脚本；不要要求学员配置 alias：

```text
node "<skill目录>/bin/vibehub" <命令>
```

## 职责边界

**AI 负责**理解和沟通：

- 判断用户只是咨询、查看状态，还是明确要求提交。
- 检查项目结构，理解玩法和核心操作，发现并修复作品本身的问题。
- 从作品内容推导清晰的作品名称和一句话介绍，从本次改动推导简短的更新说明，并从实际玩法推导核心操作路径。
- 用学生听得懂的话解释诊断和老师反馈；需要修改时先复现，再修改和验证。

**脚本负责**不能靠猜的动作：

- 兑换邀请码、创建或关联作品、保存目录绑定和切换营地连接。
- 调用 VibeHub API、携带凭证、过滤敏感文件、构建、打包和上传。
- 内容判重、状态查询、审核记录和安全预览。

不要自行猜测 API、拼接上传请求、读取或回显 token，也不要绕过脚本的敏感文件过滤。

## 操作流程

### 连接营地

用户已经给出邀请码并要求接入时，先运行：

```text
node "<skill目录>/bin/vibehub" bind <邀请码>
```

如果平台提示第一次进入需要补充资料，只问学员两个字段，不要猜：

- 真实姓名（必填，只给老师看）；
- 公开昵称（可选，会显示在作品集合里）。

然后重试：

```text
node "<skill目录>/bin/vibehub" bind <邀请码> --name "真实姓名" --nickname "公开昵称"
```

如果平台提示姓名与邀请码不一致，停止重试并让学员联系老师确认，绝不能换姓名碰撞测试。脚本不会把真实姓名写进本地凭证或输出到日志。

没有邀请码时只问这一项。绑定后告诉学员实际连接到的营地和作品，不要根据邀请码前缀猜营地。同一套 Skill 可以连接多个营地：

```text
node "<skill目录>/bin/vibehub" camps
node "<skill目录>/bin/vibehub" use <连接标识>
```

执行部署前如果无法确定目标作品，先列出连接并让学员选择完整连接标识。

### 确定新作品或已有作品

每个本地目录都必须绑定到一个明确的 VibeHub 作品。脚本把目录绑定保存在 `.vibehub/project.json`，并自动加入当前 Git 仓库的本地 exclude；不要手动编辑、复制或提交这个文件，也不要向里面写 token、邀请码、cookie、真实姓名等敏感信息。

先检查当前目录是否已有有效绑定：

- 已有绑定：这是已有作品的新版本，直接继续 `deploy`，不要另建作品。
- 没有绑定，且用户明确要做新作品：先运行 `camps`。只有一个连接时可直接运行 `project create`；有多个连接时必须用 `--from <完整连接标识>` 明确选择在哪个营地创建，绝不能使用 global active 猜测。一个学生可以自助创建多个作品，不设数量上限。
- 没有绑定，且用户明确要更新平台上的已有作品：先运行 `camps`，再用它显示的完整连接标识运行 `project link`。不能只填营地名或依赖当前 active 连接。
- 无法判断是新作品还是已有作品时，只问这一项，不要猜。

```text
node "<skill目录>/bin/vibehub" camps
node "<skill目录>/bin/vibehub" project create --title "作品名" --from <完整连接标识> "<作品目录>"
node "<skill目录>/bin/vibehub" project link <完整连接标识> "<作品目录>"
```

若 `project create` 因网络或本地保存中断，原样重试同一命令；脚本会复用目录里的 pending request_id，避免重复创建。多连接时，未绑定目录会安全停止，绝不能切回 active 连接继续上传。

复制项目目录也会复制 binding，但复制不会自动获得部署权限。CLI 会在构建和联网前停止；只有用户明确要让同一个平台作品对应第二个本地目录时，才对新目录执行一次 `project link <完整连接标识>` 完成登记。

用户在同一条完整请求里已经给出安装、邀请码和部署要求时，这些动作属于一次连续授权：安装和绑定成功后，判断新作品或已有作品并立即继续部署，不要索要第二段指令，也不要再次要求确认。

### 提交网页游戏

只处理浏览器可运行的网页项目，不研究 Unity、Godot 或应用商店发布。先做只读检查：

- 找到 `index.html`、`package.json` 和可能的构建脚本。
- 理解游戏的进入方式、胜负或目标、键鼠/触屏操作和声音要求。
- 若已有测试或检查命令，按项目约定运行；不要擅自更换技术栈。
- 不要把密码、API key、私人信息写入公开网页。

用户明确说“部署、提交、交作业”即授权创建一个私密待审版本；这不等于公开发布。若用户只是问“能不能部署”，只检查并说明，不要提交。

尽量从项目和对话中推导 `summary` 与 `flows`；只有确实无法判断时才问一个简短问题。随后运行：

```text
node "<skill目录>/bin/vibehub" deploy --title "作品名称" --tagline "一句话介绍" --summary "本次更新说明" --flows "开始游戏,完成主要目标,重新开始"
```

脚本会自动构建、寻找常见产物目录、检查首页、过滤密钥和无关目录、打包上传并进入老师审核队列。完成后明确告诉学员：已经提交待审版本，但还没有公开上线。

### 状态、预览与退回修改

```text
node "<skill目录>/bin/vibehub" status
node "<skill目录>/bin/vibehub" logs
node "<skill目录>/bin/vibehub" open
```

`status`、`open`、`logs` 都按当前目录的绑定选择作品连接，不按 global active。执行前先进入作品目录；多连接且当前目录没有绑定时必须停止，再用 `project link` 明确关联。

- 问“上线了吗”时先运行 `status`，不要猜。
- 问“老师为什么退回”时先运行 `status` 和必要时的 `logs`，不要先让学员复制反馈。
- 解释诊断时区分完成度、验证覆盖率、不适用项和需人工确认项。
- 用户要求“看看问题”时只诊断；用户明确要求“改好并重新提交”时，按反馈复现、修改、验证，再次部署。
- 预览只能通过 `open` 安全打开，不要复制或传播带临时凭证的地址。

## 平台数据能力

作品需要少量数据或上传文件时，不要让学员另写后端。页面会注入全局 `vibehub` 对象：

```javascript
await vibehub.save('scores', { player: '小明', score: 120 });
const scores = await vibehub.list('scores', { limit: 20 });
const url = await vibehub.upload(file);
const visits = await vibehub.counter('visits');
vibehub.storage.set('draft', { level: 2 });
```

不需要 import、密钥或额外配置。
