# 学员身份、名单与预览状态同步设计

日期：2026-08-14  
状态：已确认，进入实现

## 背景

VibeHub 目前把邀请码当作唯一身份入口，但邀请码、学员姓名和作品之间没有稳定关联。首次兑换学生码时，系统会创建名为“新学员”的用户和“我的作品”，因此老师端、学生端和审核列表无法可靠辨认学员。

另有一个已定位的状态同步问题：老师审核通过后，服务端会让待审预览失效并切换为正式作品；学生页只在诊断进行中轮询，审核期间停止刷新，所以旧页面仍请求已失效的预览并显示“找不到这个预览”。刷新页面后即可恢复，说明问题是客户端状态过期，不是作品丢失。

## 目标

1. 名单、邀请码、账号和作品可以分步建立、后续补齐，不强迫老师按固定顺序操作。
2. 学员第一次使用未分配的邀请码时可以自行补充姓名；老师可以核对、更正并标记已确认。
3. 老师管理端始终以真实姓名辨认学员，同时显示公开昵称、邀请码状态和作品状态。
4. 公共作品集合默认只显示昵称；只有获得学员同意后，老师才能切换为真实姓名展示。
5. 兼容网页登录和 VibeHub Deploy 两种入口。
6. 审核通过后学生页自动切换到正式作品，不再展示失效预览的误导性错误。

## 核心原则：松耦合、默认引导、不强制顺序

新增独立的营地名单记录。名单记录可以先于邀请码存在，也可以在邀请码已生成、甚至已被使用后再关联。

- 名单先录入：老师可批量粘贴姓名并生成对应邀请码。
- 邀请码先生成：老师可稍后把姓名绑定到已有邀请码。
- 学员先兑换：学员填写姓名，系统创建“学员自填、待老师确认”的名单记录。
- 临时学员：老师仍可发未分配的备用码，不阻塞临时加入。

界面给出推荐操作，但不把推荐流程变成硬性前置条件。

## 数据模型

新增 `camp_roster`：

| 字段 | 说明 |
| --- | --- |
| `id` | 名单记录 ID |
| `camp_id` | 所属营地 |
| `real_name` | 真实姓名，仅学生本人和老师可见 |
| `display_name` | 公共昵称 |
| `user_id` | 已绑定账号，可为空 |
| `source` | `teacher` 或 `student` |
| `verification_status` | `verified` 或 `self_reported` |
| `created_at`, `updated_at` | 时间 |

在 `invites` 增加可空的 `roster_entry_id`。约束如下：

- 一个名单记录最多关联一个邀请码；一个邀请码最多关联一个名单记录。
- 同名学员允许存在，不能以姓名作为唯一键。
- 账号建立后，`camp_roster.user_id`、`users.real_name` 和邀请码绑定对象在同一事务中写入。
- 现有 `users.display_name` 继续作为公共昵称；`users.real_name` 继续作为私有姓名。

## 首次兑换流程

### 未预分配姓名的邀请码

学生输入邀请码后，服务端返回 `profile_required`，网页登录显示姓名表单；AI Agent 收到同样的结构化错误后询问学员姓名，再重试绑定。

- 真实姓名必填，1–40 字。
- 公共昵称可选，1–40 字；留空时使用不含真实姓名的营地创作者编号。
- 成功后创建 `source=student`、`verification_status=self_reported` 的名单记录。

### 已预分配姓名的邀请码

学生输入邀请码后确认姓名。姓名一致才绑定；不一致返回 `profile_mismatch`，不修改邀请码和账号，并提示联系老师。匹配只做空白和常见全半角规范化，不做模糊猜测。

### 已绑定的邀请码

保持现有登录行为，不再次要求填写姓名。网页登录不会额外占用 Skill 设备名额；AI/Skill 设备限制保持现有规则。

## 姓名编辑与确认

- 学员可随时修改公开昵称。
- 学员自填且尚未确认时，可修正真实姓名。
- 老师可修改真实姓名、公开昵称，并把记录标记为“已确认”。
- 老师修改和确认写入审计日志，不在普通运行日志记录姓名。
- 学员页面显示“真实姓名（仅老师可见）”和“公开昵称”。

## 老师管理端

邀请码页增加“深圳营学员名单”式名单区，但组件对所有营地通用：

1. 可选粘贴名单，一行一个姓名；生成时按行创建名单与邀请码。
2. 原有“只生成若干邀请码”继续保留。
3. 可导入“姓名 + 已有邀请码 + 可选昵称”，用于补录历史营地。
4. 列表显示真实姓名、公开昵称、邀请码掩码、绑定状态、确认状态和作品状态。
5. 每个邀请码复制给学员的说明使用自己的邀请码，不串码。

老师端的项目、审核队列、营地概览优先显示真实姓名，并在需要时同时显示昵称；公共集合仍由 `display_name` 控制。

## 公共隐私

- 默认 `nickname`：只公开昵称。
- `camp_only`：不展示个人姓名。
- `realname`：必须由老师明确勾选“已获得学员同意”，服务端才接受，并记录同意时间与操作者。
- 真实姓名不得进入 URL、预览 claim、邀请码转发文案、普通日志或公开 API。

## 深圳营回填

以《深圳营学员名单.md》顺序和本次提供的邀请码顺序配对 11 名学员；剩余 4 个码保持未分配备用码。

- 两位已明确提供昵称的学员分别使用“笑笑”和“小麦”。
- 其余 9 人使用隐私安全的“深圳创作者01”至“深圳创作者09”，学员可自行修改。
- 已绑定邀请码只补充名单关联和真实姓名；只有现有昵称为空或为“新学员”时才替换昵称，绝不改动作品、版本、审核记录或 token。

生产回填前使用 SQLite 在线备份；导入在单一事务中执行，重复运行必须幂等。

## 预览状态同步修复

学生项目查询在以下任一条件满足时每 3 秒刷新：

- 诊断为 `running` 或 `stale`；
- 存在 `pending_version`。

待审预览授权返回 404 时，页面立即刷新项目数据并显示“作品状态刚刚变化，正在同步”。若审核已通过，界面切换为正式访问地址；若被退回，切换为修改后重新提交。不会把服务端正常失效的旧预览解释为作品丢失。

## 错误与安全边界

- 所有身份绑定、名单关联和项目创建在 `BEGIN IMMEDIATE` 事务内完成，并在事务内重读邀请码状态。
- 跨营地读取或修改名单统一返回 404。
- 资料不完整返回 409 `profile_required`；姓名不匹配返回 409 `profile_mismatch`。
- 姓名不匹配计入现有邀请码失败限流，防止枚举。
- 输入拒绝控制字符，统一 trim，限制长度。
- 导入只接受目标营地已有的完整邀请码；不自动创建未知码。

## 验收

- 老师可按“名单先、码先、学生先”三条路径完成绑定。
- 学生网页登录与 AI 部署首次都能补名，之后可正常重复登录。
- 老师端能用真实姓名找到学生和作品，学生端能看到自己的姓名与昵称。
- 公共集合默认不泄露真实姓名。
- 深圳 11 名学员与 11 个码准确绑定，4 个备用码不分配。
- 老师审核后，已打开的学生页面无需手动刷新即可从待审预览切换到正式作品。
