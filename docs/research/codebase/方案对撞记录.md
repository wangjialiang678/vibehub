# 两份独立架构方案的对撞结论

**方法**：给 Codex（gpt-5.6-sol, xhigh）一份任务简报（`docs/research/codex-brief.md`），要求它**不看别人的方案**，独立从产品需求 + 原型 + 存量资产推导架构。同时我自己写一份。然后逐项对撞。

- Codex 方案：[architecture-proposal-codex-sol.md](architecture-proposal-codex-sol.md)（819 行，含网页检索的价格与安全文档引用）
- 我的方案：[../../specs/architecture.md](../../specs/architecture.md)

## 一、独立收敛到同一结论的部分（可信度高）

两份方案在没有互相参考的情况下得出相同判断，这些可以当作稳定结论：

| 结论 | 说明 |
|---|---|
| 学员作品 = 静态站 + 平台托管数据能力 | 都明确否决"学员部署任意后端进程" |
| 2 vCPU 机器不能跑学员后端 | 容量测算一致（每进程 40–80 MB，几十个就吃满） |
| Node/TypeScript 模块化单体 + SQLite(WAL) + nginx | 都反对微服务、反对 k8s |
| 作品与预览用独立泛子域名 | 都指出必须与平台域隔离 |
| 老师审核是正式发布的唯一闸门 | AI 诊断不得自动放行 |
| 分数由确定性检查器算，模型只翻译 | 都从"百分比必须可解释"这条硬要求倒推出同一架构 |
| 版本不可变 + 原子切换 + 驳回不影响线上旧版 | 一致 |

## 二、Codex 比我强的地方（已采纳）

### 1. 评分要有 `applicability`，不适用项不进分母 ⭐

我原设计是固定权重（前端 45 / 服务端 30 / 核心功能 25）。**这有个真实缺陷**：一个纯展示型作品（比如「光合日记」）本来就不需要服务端，按我的算法它永远只能拿 70 分，系统会一直说它"需要继续完善"——学员会觉得系统在骗他。

Codex 的做法是每个检查项带 `applicability`，只有 applicable 的项进分母。**已采纳**，见 architecture.md §5.2。

### 2. `evidence_level` 证据分级 ⭐

需求文档 §14.6 明确要求「区分『已经验证』『AI 推断』和『仍需人工确认』」——**我的方案完全漏掉了这条**。Codex 给出四级：`verified` / `client_reported` / `ai_inferred` / `human_required`，并强调"客户端上报的结果不得标为已验证"。**已采纳**，见 §5.2b。

### 3. `is_blocker` 独立于分数，不偷偷封顶

有阻塞问题时显示「81%，存在阻塞问题」，而不是把 81 硬改成 59。分数和发布判断分别可解释。**已采纳**。

### 4. 版本保留策略与磁盘容量建模

我完全没算磁盘。Codex 算了：300 项目 × 3 份产物 × 20 MiB ≈ 18 GiB，加余量 24 GiB，79 GB 可容纳，但**必须有配额、清理任务和告警**。**已采纳**，见 §4.4。

### 5. 「浏览器里的 project key 不能当秘密」

我写的"服务端签发的 project key"暗示它是密钥。Codex 指出：作品是公开静态页，任何写进去的东西都等于公开。保护必须来自服务端策略。**已采纳**，见 §2.1b。

### 6. 成本估算给了真实定价与出处

我只写了"几厘到一分"的手感估算。Codex 引用腾讯云 TokenHub 2026-07-16 公布价格（输入 1 元/百万、输出 4 元/百万）算出单份约 0.01 元、一场营 5–15 元。**已采纳并保留出处**。

### 7. policy 版本化 + 产物哈希失效

报告唯一键含 `policy_version` 与 `artifact_sha256`；权重变更必须新建 policy version，否则历史报告不可复算。**已采纳**。

## 三、我认为 Codex 判断有误的地方

### ❌ 「ai-game-camp-platform 的模型网关是 501 stub，不能当已完成服务」

Codex 读了该仓库的 README（写于 2026-06-20 M0 骨架阶段，声明"P0 业务路由当前是契约 stub"），据此建议不复用。

**我核查了源码，这个判断是错的**：

```
app/gateway/router.py                33 行   0 处 501
app/common/gateway_service.py       411 行   含 check_safety / authenticate_student /
                                             _check_rate_limit / _check_quota / 用量计量
tests/test_gateway.py                        存在
```

仍是 501 stub 的只有 `app/board/`（23 行）和 `app/assets/`（17 行）——这两个本来就是 README 声明的 P1 模块。**README 过时了，M1–M3 后来由 Codex 闭环开发完成。**

**结论：模型网关可以直接复用**，且它已经把"未成年人安全过滤 + 按学员配额 + 中文错误文案"都做好了，正是 VibeHub 需要的。

> 教训：**摘要/README 不等于源码事实**。涉及"能不能复用"这类结论，必须读实现。

## 四、保留分歧（我做了判断，附退路）

### 分歧 1：服务端要不要跑无头浏览器（P0）

| | 主张 | 理由 |
|---|---|---|
| Codex | P0 不跑，推到 P1 独立 runner | 生产机同时持有数据库、SSH、云密钥，不该让不可信代码在同一爆炸半径 |
| 我 | **P0 跑，附硬缓解** | ①「页面能不能打开」是学员最常翻车处，没它诊断可信度大降 ②要靠它产出截图喂「现在的项目长这样」和审核缩略图 ③这不等于执行构建脚本，只是像普通访客一样打开一个公开页面 |

**我的裁决：P0 保留**，但必须配套独立低权限用户、不禁用 Chromium 沙箱、15 秒硬超时、内存上限、禁止访问内网段与云元数据地址（169.254.169.254）、串行队列、失败降级。

**退路**：若压测发现资源超预期或安全评估不接受，改为独立 runner——只需换诊断流水线的一个执行器，评分模型与报告结构不变。

### 分歧 2：BaaS 是 P0 还是 P1

| | 主张 |
|---|---|
| Codex | P0 只发静态站，BaaS 放 P1，缩小首期面 |
| 我 | BaaS 在 P0 |

**这个分歧不该由我们裁决，应该由事实裁决**。Codex 自己给出了正确的裁决条件（它的"开工前必须验证"第 6 条）：

> 首期课程是否强依赖"作品运行时上传、共享数据或 AI 调用"？

- 第一场是「城市声音地图」这类要录音存数据的作品 → BaaS 是 **P0 阻塞项**
- 第一场以展示型网页为主 → BaaS 可推 **P1**

这挂在〔决策 7〕（首场落地场次）上。**在答案到来前，工程上按"BaaS 先定契约、实现排在静态链路之后"推进，两种结论都不返工。**

### 分歧 3：凭证形态

| | 主张 |
|---|---|
| Codex | 短期访问凭证 + 可轮换刷新凭证 |
| 我 | 长期不透明 token + 即时吊销 |

**我保留自己的方案**：营地场景下 skill 跑在学员笔记本上，长期 token 存 0600 文件是业界常规做法（`gh` CLI 同理）。刷新凭证增加的复杂度，在"老师可即时吊销 + 邀请码撤销级联失效"已经能覆盖风险的前提下，收益不足。

**退路**：token 表已有 `expires_at` 字段，将来要改成短期+刷新，加一张 refresh 表即可，不动业务逻辑。

## 五、Codex 提出的、我原本没列的待验证项（已并入）

1. 腾讯云安全组、主机防火墙**和运营商链路**能否开放 443（我只想到前两者）
2. DNS API 凭证能否**限权到 `_acme-challenge`**（最小权限，我没想到）
3. 「主域名已备案」**不自动等于所有接入细节已验收**——子域名境内访问要实测
4. 超脑上传平台的 VOD/COS 生产链路状态（其测试计划明确把真实云上传排除在离线测试外）
5. 未成年人作品的**公开署名规则、内容审核清单、投诉与下架负责人**（这是运营缺口，不是技术缺口）

第 5 条尤其值得注意：**「谁负责处理投诉和下架」这个问题，产品设计再好也替代不了一个具体的人。** 开营前必须落实到人。
