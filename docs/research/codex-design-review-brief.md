# Codex Sol 任务：VibeHub 整体设计方案批判性审查

## 你的角色

你是**独立的批判性审查者**，不是协作者。你的价值在于**找出问题**，不在于确认方案可行。

**明确要求：不要写"整体设计合理"这类结论。** 如果你审完真的认为某部分没问题，就跳过它，把篇幅留给有问题的地方。**一份只说好话的审查报告等于没做审查。**

## 只读，不改代码

- **不要修改任何代码文件。** `web/` 和 `server/` 都有其他 codex 任务正在并行写入，你碰了会造成冲突。
- 你只写一个文件：`docs/research/codebase/design-review-sol.md`

> 如果你认为某条决策会导致**严重后果**（数据泄露、开营当天崩、法律风险），仍然要写出来，
> 但要写清楚"在不推翻决策的前提下如何缓解"，而不是简单建议改回去。

## 请重点审查的方向

按你判断的严重程度排序输出，不必平均用力：

1. **路径式网址造成的后果有没有被处理干净**
   - 所有作品共享一个 origin：cookie、localStorage、sessionStorage、Service Worker、IndexedDB、权限授予（麦克风/定位）会不会互相串？
   - 已有的缓解（控制台换到 `hub.` 子域、SDK 的 storage 命名空间）够不够？漏了什么？
   - 一个学员作品能不能影响或劫持另一个学员的作品？

2. **诊断评分体系的可信度**
   - `applicability` 分母、`evidence_level`、`is_blocker` 独立于分数——这套规则有没有能被绕过或产生误导的情况？
   - 有没有可能出现"分数很高但作品其实是坏的"或反过来？
   - 权重设定（20/20/20/20/20/10）有没有明显不合理的地方？

3. **安全边界**
   - 解包规则有没有漏洞（zip slip 变体、tar 特殊条目、超长路径、Unicode 归一化攻击）？
   - BaaS「公开可读、限流可写」这个默认策略，在营地场景下会不会出事？
   - 学员作品能不能通过 BaaS 接口读到别的项目的数据？
   - 鉴权模型（不透明 token + scope）有没有提权路径？

4. **7/29 能不能上线**
   - 对照 `docs/handbook/deployment.md` 的前置阻塞项，还缺什么？
   - 有没有"上线当天才会暴露"的问题（并发、首次运行、空数据状态、老师同时审核、30 人同时提交）？
   - 如果只剩 4 天，你会砍掉什么、加固什么？

5. **产品逻辑漏洞**
   - 五维状态机有没有能进入的坏状态（比如 pending 和 live 指向同一版本、驳回后状态错乱）？
   - 老师审核流程在多老师、并发、误操作下会怎样？
   - 学员换设备、丢邀请码、退营后作品归属这些边界情况

6. **文档与实现是否一致** —— 设计文档承诺了但代码里没有的，或代码做了但文档没写的

## 输出格式

写到 `docs/research/codebase/design-review-sol.md`，结构：

```
# 设计审查（Codex Sol）
> 审查时间 / 审查范围 / 一句话结论

## 严重问题（会导致开营失败、数据泄露或法律风险）
每条：问题描述 → 触发条件（具体到怎么复现）→ 影响 → 建议修法 → 修复成本估计

## 值得修但不阻塞上线
（同上格式）

## 我认为设计得对、但理由和文档写的不一样的地方
（这类往往说明文档的论证是错的，即使结论对）

## 我不确定的地方
明确写出你判断不了什么、需要什么信息才能判断
```

## 写作要求

- **每条问题必须给出具体的触发条件**，不接受"可能存在风险"这种没法验证的说法
- 事实与推测分开，推测显式标注
- 涉及外部事实（标准、法规、库行为）给出处
- 中文
- 不写空话套话，不写"建议进一步评估"这种没有信息量的结论
